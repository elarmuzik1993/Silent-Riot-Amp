## 1. Scope of AI Usage

AI tools were used, under the author's direction, for:

| Area | What the AI tools did |
|---|---|
| Source code | Drafted and implemented C++ DSP and GUI code from the author's specifications and instructions |
| Tests and tools | Wrote Catch2 tests, the sign-off render and analysis tools, and measurement probes |
| Debugging and review | Helped root-cause defects, ran measurements, and reviewed code |
| Documentation | Drafted the README, user manual, developer docs, CHANGELOG and the dated records in `docs/records/` |

Tools used: **Claude / Claude Code** (Anthropic) and **ChatGPT / Codex** (OpenAI).

AI tools were **not** used to:

- choose what the amp is, how it sounds, or what it does — those are the author's decisions
  (see section 3);
- copy, adapt or translate code from other amp simulators. The originality statement in
  [`CREDITS.md`](CREDITS.md) applies to AI-assisted code exactly as to any other code;
- generate audio, impulse responses or recordings presented as real. The test IRs are synthetic
  and generated by a script in this repository (`tools/make_ir_fixtures.py`).

## 2. AI-Assisted Workflow

Every change, whoever or whatever typed it, goes through the same steps:

1. **The author sets the task.** Each piece of work starts from the author's request, a written
   plan in [`docs/plans/`](docs/plans/), or a defect the author reported.
2. **The AI drafts it** inside the rules the author wrote for the project:
   [`AGENTS.md`](AGENTS.md), [`CLAUDE.md`](CLAUDE.md) and the current-state note
   [`.agents/STATE.md`](.agents/STATE.md). These record the project's conventions, its known
   pitfalls and the decisions the author has made, so the tools work to them instead of
   improvising.
3. **It has to pass the checks.** Nothing is done until `bash scripts/verify.sh` passes: the
   build, about 450 automated tests, and static checks on licences, links and UI text. Fixes and
   features come with tests.
4. **The sound is checked by measurement and by ear.** Tone changes are judged against the
   sign-off gates ([`docs/dev/tone-signoff.md`](docs/dev/tone-signoff.md)) and by the author
   listening. The sound is frozen at `tone-v1` by the author's ear sign-off; an automated test
   fails on any change to it, and the references move only after the author approves an A/B
   comparison ([`docs/dev/tone-lock.md`](docs/dev/tone-lock.md)).
5. **The author reviews and merges.** Changes arrive as pull requests. The author decides what
   is merged, sent back or dropped, and tests the plugin on real hardware.

The design decisions, measurements and their reasons are kept in the repository
(`docs/plans/`, `docs/records/`, `CHANGELOG.md`), so anyone can see how and why the code got
the way it is, and re-run the measurements.

Individual commits and pull requests do not carry AI attribution lines. That is a deliberate
choice to keep the history clean and readable, not to hide anything: AI assistance is part of
how the whole project is built, and this document discloses it once, for all of it.

## 3. Human Authored Content / Substantial Human Input

The author, Boris Miscenco, art-directed the whole project. In practice that meant:

- **The sound.** The author set out the sound Silent Riot should have and pursued it through
  repeated listening rounds, judging every voicing change by ear. The shipped tone (`tone-v1`)
  is the author's sign-off, and it changes only with the author's approval after an A/B.
- **The architecture.** The author decided the product's architecture: an original fictional
  amp in the cascaded-ECC83 / EL84 push-pull family, its signal chain and controls (GAIN,
  SHAPE, VOLUME, 15W/7W, CAB), the effects, and what the plugin does and does not do. Where the
  AI tools proposed designs or alternatives, the author chose between them.
- **The look.** The faceplate, knobs, toggles, cab view and layout were directed, iterated and
  approved by the author.
- **Direction.** The tasks, priorities and plans; what was built, in what order, and what was
  rejected for not meeting the bar.
- **Testing in use.** Playing the plugin, finding problems by ear and on real audio
  interfaces, and reporting them.
- **Approval.** Every change merged into the project was reviewed and approved by the author.

The AI tools proposed, implemented and measured; the author directed, decided and approved.
The AI tools are not authors of the project.
